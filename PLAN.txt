1. STRICT ARCHITECTURAL & HACKATHON CONSTRAINTS
================================================================================
- Stack: Node.js, Express, native 'mongodb' driver (DO NOT use Mongoose or any other ODM).
- Packages: Strictly express, cors, and mongodb (already in package.json). No other npm packages.
- Database: mongodb://127.0.0.1:27017, Database name: 'Hack_SmartCanteen'.
- IDs: All MongoDB lookups must cast string IDs using `new ObjectId(id)` and return 400 if the ID is not a valid 24-character hex string.
- Error format: Always return JSON in the format `{ "error": "Human-readable explanation" }`.
- Client Trust Rule: The frontend NEVER calculates prices, totals, or prep times. The Express server retrieves values directly from MongoDB.
- State Machine Rule: Statuses must strictly follow:
  "placed" -> "preparing" -> "ready" -> "collected".
  Any illegal jump or backward move must immediately return HTTP 400 Bad Request.

================================================================================
2. DATABASE SCHEMAS & BUSINESS RULES
================================================================================
A. `menu` collection:
   - `_id`: ObjectId
   - `name`: string (e.g., "Crispy Chicken Roll")
   - `amount`: number (price in ₹, must be > 0)
   - `availableUnits`: number (integer >= 0; physical stock count)
   - `prepTime`: number (time taken to make in minutes, e.g., 10)
   - `spiceLevel`: number (integer from 1 to 5, e.g., 0 + no spice, 5 = Extra Hot 🌶️🌶️🌶️🌶️🌶️)
   - `dietaryType`: string (strictly one of: "veg", "egg", "non-veg")
     - "veg" ➔ Rendered with 🥦 Veg
     - "egg" ➔ Rendered with 🥚 Egg
     - "non-veg" ➔ Rendered with 🥩 Non-Veg
   - `category`: string ("Breakfast", "Snacks", "Beverages", "Meals")

B. `orders` collection:
   - `_id`: ObjectId
   - `tokenNumber`: string (e.g., "T-101", sequential)
   - `customerName`: string
   - `usn`: string (uppercase, e.g., "1RV21CS001")
   - `items`: array of { menuId: ObjectId, name: string, amount: number, qty: number, prepTime: number, spiceLevel: number, dietaryType: string }
   - `totalAmount`: number (computed on server: sum of qty * item.amount)
   - `estimatedPrepTime`: number (computed on server: max prepTime among ordered items, in minutes)
   - `status`: string ("placed" | "preparing" | "ready" | "collected")
   - `createdAt`: Date

C. Critical Inventory & Concurrency Rule:
   When placing an order (`POST /orders`):
   - For each item, verify `availableUnits >= item.qty`.
   - If stock is insufficient, return 409 Conflict: `{ "error": "Only X units of '<Item Name>' remaining in stock" }`.
   - If sufficient, atomically decrement `availableUnits` by `qty` using MongoDB `$inc: { availableUnits: -qty }`.
   - If an order is cancelled or an item is deleted, restore units.

================================================================================
3. REST API SPECIFICATION
================================================================================
- `GET /menu`: Fetch all menu items. Supports query filters:
  - `?dietaryType=veg|egg|non-veg`
  - `?maxSpice=1..5`
  - `?category=...`
- `POST /menu`: Add new menu item with strict validation:
  - `name`: non-empty string
  - `amount`: number > 0
  - `availableUnits`: integer >= 0
  - `prepTime`: number > 0
  - `spiceLevel`: integer between 1 and 5 (return 400 if outside 1-5)
  - `dietaryType`: must be "veg", "egg", or "non-veg" (return 400 if invalid)
- `PATCH /menu/:id/stock`: Add or set `availableUnits` (restock item). Returns 200, 400, or 404.
- `POST /orders`:
  Accepts: `{ customerName, usn, items: [{ menuId, qty }] }`.
  1. Validates non-empty customer name, valid USN format, valid ObjectIds, positive quantities.
  2. Queries `menu` for all requested items. Returns 404 if any item doesn't exist.
  3. Checks `availableUnits`. Returns 409 if requested quantity exceeds stock.
  4. Calculates `totalAmount` and `estimatedPrepTime` server-side.
  5. Atomically decrements `availableUnits` for each ordered item.
  6. Inserts order with sequential token (e.g., "T-101") and status "placed". Returns 201.
- `GET /orders`: Returns all active orders sorted by `createdAt` descending.
- `GET /orders/:id`: Returns single order details (for customer token live tracker).
- `PATCH /orders/:id/status`:
  Accepts: `{ status }`.
  Enforces transitions: "placed" -> "preparing" -> "ready" -> "collected".
  Returns 400 if invalid jump; 404 if order not found; 200 on success.
- `GET /orders/stats`: MongoDB `.aggregate()` returning:
  `{ totalRevenue, totalOrders, activeOrdersCount, topSellingItem }`.
